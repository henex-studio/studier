# Studier whole-site audit, 5 September 2026

Requested by the operator after the tone test role links, wording strip and editor footer work landed. Covers the live database and the front end. Nothing in this document has been changed in the code. It is a list of findings for the operator to prioritise.

**Database audited:** Supabase project `nyljkalkojpexliomzzf`, the live production database. There is no development branch, which is itself finding A7.

**Method.** Supabase security and performance advisors, direct SQL against the live schema for row level security state, policy definitions and function bodies, migration comparison between the repository and the applied list, and a read of every page and component in `src/`.

**Severity.** High means fix before the next release. Medium means fix soon, it is either user visible or it weakens a stated guarantee. Low means worth doing when the area is next touched.

---

## What is sound

Worth stating first, because several of these are guarantees the privacy policy makes and they hold up.

Every table in the `public` schema has row level security enabled. All sixteen of them.

No anonymous role appears in any select policy on any response table. Every select policy on `task_responses`, `final_responses`, `participant_sessions`, `tone_responses`, `tone_gate_responses` and `tone_sessions` is restricted to `authenticated` and gated on `is_study_owner(study_id) OR is_admin()`. The privacy policy sentence "Studier gives an unsigned-in visitor no access to any response at all" is accurate.

Participants never write to a table directly. There are no insert policies on the response tables at all. Every participant write goes through a `SECURITY DEFINER` function that checks the study is published first.

`start_tone_session` is well built. It validates the role name against a fixed list, confirms the study is published, confirms the requested role is active in `active_roles_json`, and runs with `search_path` set to empty. The role link change made this week cannot be used to answer as a role the creator switched off, even by editing the URL by hand.

The fifteen migration files in `supabase/migrations/` all correspond to applied migrations on the live database. Repository and database agree.

Clearing response data handles both study types correctly, deleting the tone tables for a tone test and the tree tables for a tree test.

CSV export exists for both study types, two exports each.

All ten guide screenshots carry descriptive alt text of a quality most projects never reach.

## A. Database

### A1. Three access control functions have a mutable search path. Medium.

`is_admin()`, `is_study_owner(uuid)` and `is_study_published(uuid)` are all `SECURITY DEFINER` and none of them sets `search_path`. These three functions are the ones every row level security policy in the database calls to decide who sees what. A `SECURITY DEFINER` function without a fixed search path is the standard privilege escalation pattern in Postgres, because an attacker who can create an object in a schema earlier in the search path can shadow the table the function reads.

Exploitability here is low, since the `authenticated` role in Supabase cannot create schemas or tables. The reason to fix it anyway is that these are the three functions that gate all access control, so they are exactly the wrong place to leave a known weakness. `delete_my_account` and `start_tone_session` already set it correctly, so the fix is to bring the older three up to the same standard.

Fix is one migration adding `SET search_path = public` to each of the three.

### A2. Anonymous visitors can call the access control helpers directly. Low.

`is_admin()`, `is_study_owner(uuid)` and `is_study_published(uuid)` are all callable over the REST API by the `anon` role. `is_admin()` and `is_study_owner()` return false for an anonymous caller and leak nothing. `is_study_published(uuid)` will confirm whether a given study id is published, which is a small information leak and only to someone who already has a valid study id.

Participants never need any of the three. Revoking execute from `anon` on all three costs nothing.

The advisor also flags `rls_auto_enable()` as anon executable. I read the function. It is an event trigger function, it already sets `search_path`, and calling it over REST cannot do anything, because event trigger functions only run from a DDL event. No action needed, recorded here so it is not re-investigated later.

### A3. Leaked password protection is switched off. Low.

Supabase Auth can check new passwords against the HaveIBeenPwned corpus and refuse known-breached ones. It is currently disabled. This is a toggle in the Supabase dashboard under Authentication, not a code change.

### A4. Ten foreign keys have no covering index. Low now, Medium later.

`studies.owner_id`, `study_tasks.study_id`, `study_trees.study_id`, `task_responses.task_id`, `tone_gate_responses.question_id`, `tone_gate_responses.variant_id`, `tone_responses.question_id`, `tone_responses.variant_id`, `tone_sessions.assigned_variant_id` and `tone_sessions.preferred_variant_id`.

With 263 task responses and 139 tone responses in the database this costs nothing measurable. It will start to matter on a real study with a few hundred participants, and it matters most on the dashboard, which reads all responses for a study at once. Worth doing before any study with external participants runs, not before that.

### A5. Row level security policies re-evaluate `auth.uid()` per row. Low now.

Eight policies across `profiles`, `studies`, `task_responses`, `final_responses` and `participant_sessions` call `auth.uid()` directly rather than `(select auth.uid())`. Postgres re-runs the call for every row instead of once per query. Same reasoning as A4, invisible at current data volume, and a cheap fix while the tables are small.

### A6. Six tables carry two overlapping permissive select policies. Low.

`study_tasks`, `study_trees`, `study_final_questions`, `tone_questions`, `tone_variants` and `tone_test_settings` each have both an "owner admin all" policy and an "owner admin or published select" policy. Both are evaluated on every read. `profiles` has the same duplication on update.

This is not a security fault, both policies are permissive and correct. It is accumulated sediment from adding the published-read path later. Consolidating each pair into one policy would make the access rules easier to read, which matters more than the performance gain.

### A7. There is no Supabase development branch. Medium, already known.

`CLAUDE.md` section 5 states that local development and the Vercel preview both point at a Supabase development branch, and that only production points at the production database. No development branch exists. Everything points at production, and the migrations applied this week were applied straight to it.

The operator has already decided not to fix this before the merge to `main`. Recording it so the documentation and reality get reconciled afterwards, one way or the other. Either create the branch or correct section 5, because a governing document that describes a safety measure which is not present is worse than one that admits the gap.

### A8. One study type field was applied twice. Low.

The applied migration list contains `add_study_type_to_studies` twice, ten seconds apart, at versions `20260815070334` and `20260815070344`. The repository has one file for it. Harmless, since the migration is idempotent, but it means version numbers in the database do not map one to one onto files. Worth knowing before anyone tries to reconcile the two lists by counting.

## B. Front end and user experience

### B1. The Preview button on a tone test does not preview anything. Medium.

`previewPath()` in `StudyListPage.jsx` sends a tone test to `/tone-builder/:id`, which is the editor. So a tone test card shows Edit and Preview side by side and both open the same page. A tree test's Preview opens a real participant preview at `/preview/:id`.

Tone test preview does exist, as the "Preview by role" section inside the builder, so the capability is there. The button is what is wrong. Either rename it, remove it, or make it deep link to that section of the builder.

### B2. `/preview/<a tone test id>` is unguarded. Low.

`PreviewRunnerPage.jsx` contains no reference to `study_type`. Given a tone test id it will try to render a tree test and produce either an error or an empty preview. Nothing in the interface links there, so this only bites on a typed or bookmarked URL. `DashboardPage.jsx` handles the same situation correctly by dispatching on study type, so the pattern to copy already exists.

### B3. There is no not-found page. Medium.

`App.jsx` ends with `return <StudyListPage profile={profile} />`. Every unrecognised path for a signed-in user silently renders the test collection, and every unrecognised path for a signed-out user renders the sign-in page. A mistyped URL, a stale bookmark, or a link to a deleted study all end up somewhere plausible looking with no indication that the address was wrong. `/builder` with no id behaves the same way.

### B4. Four confirmations use native browser dialogs. Medium.

`window.prompt` in `StudyListPage.jsx` for clearing test data, `window.confirm` in the same file for deleting a study, in `ToneBuilderPage.jsx`, and in `StudyBuilderPage.jsx` for leaving with unsaved changes.

These are unstyled operating system dialogs. They look nothing like the rest of the site, they cannot be made to match it, and some browsers suppress them. The account deletion flow built this week does the same job properly, with an in-page typed confirmation, and is the pattern to standardise on. This one is worth raising because destructive confirmations are exactly where an interface should feel deliberate, and a grey system box is the opposite of that.

### B5. The registration form has no field labels. Medium.

`RegisterPage.jsx` uses placeholder text alone for display name, email, password and invite code. The placeholder disappears as soon as the person types, so anyone who pauses mid-form loses the labels, and screen readers get nothing reliable to announce. `LoginPage.jsx` immediately next to it does this correctly with `<label className="form-block">` and a `<span className="form-label">`. The new test title field in `StudyListPage.jsx` has the same problem.

### B6. A second role link silently keeps the first role. Low.

Verified against the database function, not guessed. If a participant opens the Audience link, answers at least one question, and later opens the Agency link in the same browser, `start_tone_session` returns their existing session unchanged, because the role locks once answers exist. This is the correct behaviour. The gap is that nothing tells them. The page will say "You are answering as Audience" while they arrived through a link they were told was for Agency, and they get no explanation of the mismatch.

Worth one sentence of copy when the link role and the session role disagree.

### B7. Two loaders discard their error. Low.

`ToneTestLinks.jsx` and the question loader in `ToneTestRunnerPage.jsx` both destructure only `data` from the Supabase response. If either query fails, the component renders as though the result were empty. In the runner that shows "No questions found for this role", which points the participant at the wrong cause.

### B8. The mobile and desktop breakpoints overlap by one pixel. Low.

`src/style.css` uses `@media (max-width: 640px)` at line 284 and `@media (min-width: 640px)` at line 1402. At exactly 640 pixels wide both rule sets apply and the result depends on source order. Every other mobile query in the file correctly uses 639. Changing line 284 to 639 makes the file consistent.

## C. Accessibility

### C1. No selectable button anywhere reports its state. Medium.

There is no `aria-pressed` in the codebase. The affected controls are the rating scale of one to five plus Not applicable, the Pass, Concern and Fail gate buttons, the preferred wording buttons, the role choice buttons, the new wording tabs, and the card and list view toggle. Every one of them shows selection through colour alone.

A sighted participant sees which rating they chose. A screen reader user hears an identical announcement whether the button is chosen or not, and someone who cannot distinguish the blue from the white gets nothing either. This runs through the whole participant flow, which is the part of the product used by people outside the organisation.

### C2. The rating scale is not announced as a single choice. Medium.

The five rating buttons are five independent buttons with no grouping and no accessible name for the group. Nothing conveys that they belong together, that only one can be chosen, or which question they belong to. Native radio inputs, or a `role="radiogroup"` with a label, would fix both this and part of C1. `StudyListPage.jsx` already uses `role="group"` with `aria-label` on the type filter, so the pattern exists in the codebase.

### C3. Text contrast is adequate. No action.

`.muted-text` is `#64748b`, which reaches about 4.8 to 1 against white. That passes the AA threshold of 4.5 to 1. Recorded so it is not re-checked.

## D. Documentation now out of date

The three changes made this week invalidated parts of the guides. This is a direct consequence of the work, not pre-existing drift.

### D1. The tone guide still describes participants choosing their own role. Medium.

`ToneGuidePage.jsx` line 116 says participants choose which role they are answering as before they start. Lines 250 and 251 say a participant opens the link, reads the welcome and privacy content, and chooses a role. With role links this is no longer what happens for anyone who receives a proper link. The guide also needs to explain that the creator now copies one link per role and sends each to the right group, which is the whole point of the change and is currently documented nowhere.

### D2. Three guide screenshots show interfaces that no longer exist. Medium.

`08-tone-participant.png` shows the "Choose your role" step, and its caption states that the role choice comes before any wording is shown. `05-tone-builder.png` predates the sticky footer on the tone editor. `01-test-collection.png` predates the role link selector on the tone test card. The capture script at `scripts/screenshots/capture.mjs` still works, so re-running it for those three is the fix.

### D3. The version history has no entry for this week's work. Low.

`VersionHistoryPage.jsx` stops at v4.04. Account deletion, the privacy policy modal, role links, the wording strip and the editor footer are all missing. The page states it lists functional updates only, and four of those five qualify.
